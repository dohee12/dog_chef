## 1. 목표

반려견마다 다음을 레시피 화면에 보여 준다.

- 먹으면 안 되는 재료를 막는다.
- 그 아이의 알레르기 재료를 막는다.
- 주의할 재료, 교차반응, 건강 상태와 품종에 따른 위험을 알려 준다.
- 판정마다 출처를 붙인다.

근거가 없는 재료는 안전하다고 추정하지 않고 "확인 안 됨"으로 보여 준다.

목업 안에 근거 데이터 JSON과 판정 함수를 넣어서 실제로 계산한다. 이 판정 함수가 서버 판정 엔진의 원형이다.

- "오리안심", "양갈비"가 '안심'·'갈비' 글자 때문에 소고기 알레르기로 잡혔다. 예외 단어를 추가했다.

## 4. 결정할 것

### 결정 1. 아래 탭 구성 — 결정됨 (2026-11-16)

**5칸 + 가운데 등록 버튼(3안)**으로 정했다: 홈 · 찜 · (+) 등록 · 먹었어요 · 내 반려견.

- 검색 탭은 없애고 홈 검색창으로 합친다.
- 찜은 레시피 사진의 ♡로 넣고 빼며, 찜 탭의 배지도 선택한 반려견 기준으로 계산한다.
- AI 멍셰프 버튼은 가운데 버튼과 겹치지 않게 조금 위로 올린다.
- 비교 자료: `docs/tab-options.html`

### 결정 2. 카테고리 — 결정됨 (2026-11-13)

**주재료 기준**으로 정했다: 전체 · 닭·오리 · 소·돼지·양 · 생선 · 채소·과일 · 곡물·고구마 · 달걀·유제품 · 계절 추천.

- 레시피 등록 때 "대표 재료"를 하나 고른다. 첫 재료를 근거 데이터로 판정해 자동으로 골라 주고, 작성자가 바꿀 수 있다.
- 기존 레시피(주식·간식·건강식·특별식)는 1:1로 옮길 수 없다. 같은 자동 추천 규칙으로 재료를 보고 다시 분류하고, 분류가 안 되는 레시피는 목록으로 뽑아 직접 고른다.
- 형태 구분(식사·간식)이 없어진다. 필요하면 나중에 카드에 작은 태그로 붙인다.

### 결정 3. AI 멍셰프 방식

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A (목업) | 근거 데이터 검색형. 문장에서 재료를 찾아 판정과 출처를 보여 줌 | 지어낸 답이 없음. 비용 0원. 바로 만들 수 있음 | "이거랑 이거 섞어도 돼?" 같은 복잡한 질문은 못 함 |
| B | LLM(Claude API)이 답하고, 근거 데이터를 넘겨 그 안에서만 답하게 함 | 자연스러운 대화 | API 비용이 들고, 답을 검증하는 장치가 필요함. 출시 전 안전성 시험이 필요함 |
| C | 1차 출시에서 뺌 | 범위가 줄어듦 | 목업의 핵심 볼거리가 빠짐 |

**추천: A로 먼저 만들고**, 사용자 질문 기록을 보고 B를 검토한다.

### 결정 4. 위험 재료가 들어간 레시피 등록

| 안 | 내용 |
|---|---|
| A (목업) | 등록을 막음. 주의 재료는 안내만 함 |
| B | 경고 후 등록은 되지만 비공개 |
| C | 경고만 하고 공개 |

**추천: A.** 앱의 핵심 약속은 "위험 재료를 추천하지 않는다"이다. B와 C는 그 약속을 깨기 쉽다.

### 결정 5. 섭취 기록 저장 (계산기)

| 안 | 내용 |
|---|---|
| A | 1차에 넣음. 반려견별 기록 테이블과 API를 새로 만듦 |
| B | 1차에서 빼고 계산과 병원 연락 버튼만 둠 |

**추천: B.** 기록은 의료 기록처럼 보일 수 있어 문구 검토가 필요하다. 계산 기능이 먼저다.

### 결정 6. 영어 원문 인용 표시

출처 시트의 인용이 영어로 나온다. 한국어 요약을 같이 보여 줄지 정해야 한다.

**추천:** 데이터에 `quote_ko`(한국어 번역) 칸을 추가하고, 원문은 접어서 보여 준다.

## 8. 서버는 Supabase로 (2026-11-16 결정)

**이유**: 기존 데이터가 Supabase에 있다. 지도교수님이 함께 개발한 구조라 데이터를 다루기 쉽다. 서버비가 들지 않는다.

지금 저장소의 NestJS 백엔드(커밋 1066e57에서 Supabase 대신 넣은 것)는 아래 기능을 Supabase로 옮긴 뒤 정리한다. 지우는 시점은 따로 정한다.

| 기능 | Supabase에서 하는 방법 |
|---|---|
| 반려견·레시피·찜·리뷰 저장 | 기존 테이블(pets, recipes, likes, reviews)과 RLS 정책(`Supabase_RLS_설정.sql`)을 그대로 쓴다 |
| 입력 검증 (몸무게 0·음수, 빈 이름) | 테이블 CHECK 제약 (예: weight 0.5~100, 이름 빈칸 금지) |
| 알레르기·건강 상태 | pets에 id 배열 칸(allergies, conditions)과 유당 민감 칸(lactose_sensitive)을 추가한다 |
| 주재료 카테고리·계절 | recipes의 category 값을 바꾸고 seasons 배열 칸을 추가한다. 기존 레시피는 변환 SQL로 다시 분류한다 |
| 찜을 반려견별로 | likes에 pet_id 칸을 추가한다 |
| 섭취 기록 (결정 5에서 넣기로 하면) | intake_logs 테이블을 새로 만들고, 같은 기록이 두 번 들어가지 않게 제약을 건다 |
| 판정 엔진 | Edge Function `judge`. 근거 데이터 JSON을 함수와 함께 배포하고, 모든 화면이 이 함수 결과를 쓴다 |
| 위험 재료 레시피 등록 거절 | 레시피 등록을 Edge Function `submit-recipe`로 받아 판정한 뒤 저장한다. 직접 insert는 RLS로 막는다 |
| 식약처 영양 DB | Edge Function이 API 키(Secrets에 저장)로 불러오고, 결과는 food_cache 테이블에 저장한다 |
| 레시피 사진 | Storage 버킷 |
| 출처 한국어 요약 | 근거 데이터에 quote_ko 칸을 추가해 함수와 함께 배포한다 |

확인할 것 (시작 전):

- 무료 플랜 제한: 오래 안 쓰면 프로젝트가 일시 정지되는지, Edge Function 호출 한도가 얼마인지. Supabase 요금 페이지에서 확인한다.
- 교수님과 기존 테이블 구조·RLS를 바꿔도 되는지, 칸 추가 방식을 맞춘다.

### 9-3. 먹은 양 입력을 "포장지로 계산"으로 바꿈 (2026-11-19)
보호자는 몇 개를 먹었는지는 알아도 몇 g인지는 모른다는 지적에 따라 g 입력을 기본에서 뺐다.
- 초콜릿·마카다미아: "포장지가 있어요/없어요" 중에서 고른다.
  - 있으면 내용량(g)을 넣고, 그중 얼마나 먹었는지(¼·½·¾·전부, 칸·개 수로 세기, 몰라요)를 고른다.
  - 칸·개 수로 세면 "전체 ○칸 중 ○칸"을 넣는다. 먹은 양은 내용량 × 비율로 계산한다.
  - 없으면 "계산할 수 없어요 · 병원에 전화"로 보낸다.
- 양파·마늘: "포장 제품이에요/그냥 양파·파·마늘이에요" 중에서 고른다. 그냥이면 계산할 수 없음으로 보내고, 품종·가루 규칙은 그대로 둔다.
- 자일리톨: 개수만 묻는다. 1개 함량은 아는 경우에만 넣고, 비우면 응급으로 본다. 포도: 개수만 묻는다(기록용).
- "먹은 무게(g)를 정확히 알아요"는 작은 링크로 남겼다.
- 판정·전화 카드·기록에는 "밀크 초콜릿 100g짜리 중 3/12칸 (약 25g)"처럼 보호자가 넣은 그대로 적는다.
- 챗봇 "3조각 먹었어요"는 칸 수 3으로 넘기고, 내용량과 전체 칸 수를 넣으라고 안내한다.
- 남은 것: "마늘 1쪽·양파 ¼개·마카다미아 1알" 같은 흔한 크기 고르기(B안). 표준 무게 출처가 생기면 품목별로 추가한다(근거 필요).
- 확인한 것: 실제 클릭·입력 시나리오 21단계, 전체 앱 시나리오, 계산 확인 스크립트(360px)를 돌렸고 모두 스크립트 오류가 없었다.
  - 밀크 100g의 ½, 8kg → 14.4 mg/kg, 물어보기.
  - 밀크 100g 중 3/12칸 → 약 25g, 7.2 mg/kg.
  - 마카다미아 30g 전부, 3.8kg → 7.89 g/kg, 병원 가기.
  - 자일리톨 2개 × 300mg, 8kg → 75 mg/kg, 응급.

### 9-4. 먹은 양을 "그림으로 고르기"로 다시 바꿈 (2026-11-19, 9-3 대체)
9-3의 포장지 방식은 단계와 입력이 많고, 내용량을 읽어 넣는 것이 현실적이지 않다는 피드백을 받아 걷어냈다.
- 초콜릿: 제품 카드 중 하나를 고른다.
  - 카드: 판초콜릿 작은 것 34g, 큰 것 70g, 초코파이류 39g, 빼빼로류 54g, 다크·코코아·다른 것(종류·무게 직접).
  - 분량: ¼·한두 입 / ½·반 개 / 1개 다 / 여러 개(개수 입력) / 몰라요.
  - 계산: 밀크 초콜릿 2.3 mg/g(Merck). 초코파이류·빼빼로류는 과자 전체를 밀크 초콜릿으로 보고 계산해 실제보다 높게 나올 수 있다고 알린다.
- 양파·마늘: 카드 4개(마늘, 양파, 가루·말린 것, 양파·마늘 든 음식)에서 고른다.
  - 마늘은 1·2·3·5쪽 또는 직접 입력, 1쪽 3g × 5배로 계산한다.
  - 양파는 ¼·½·1개, 1개 110g으로 계산한다.
  - 가루·말린 것은 병원 가기, 든 음식은 계산할 수 없음으로 보낸다. 품종 규칙은 유지한다.
- 마카다미아: 알 수만 묻는다(1·3·5·10). 1알 2.8g으로 계산한다(USDA 1 oz = 10~12알 중 작은 수 쪽).
- 자일리톨·포도: 개수만 묻는다(그대로).
- "먹은 무게(g)를 정확히 알아요" 링크로 예전 상세 입력(종류 칩 + g)을 쓸 수 있다.
- 출처와 한계:
  - 제품 무게는 판매처 표시 중량이다(컬리 가나 마일드 34g, 컬리·다나와 초코파이 39g, 빼빼로 54g 제품명). 70g 판초콜릿은 가나 마일드 70g 규격이 있다는 판매 정보로 확인했다.
  - 마늘 3g, 양파 110g, 마카다미아 28.35g/10~12알은 USDA FoodData Central 값이다. 미러 사이트로만 확인했고 원문은 미확인이다.
  - "한두 입 = ¼개"는 근거 없는 화면 가정이라 화면에 그대로 드러낸다(근거 필요).
- 확인한 것: 실제 클릭 시나리오, 전체 앱 시나리오, 계산 확인 스크립트를 돌렸고 모두 스크립트 오류가 없었다.
  - 판초콜릿 34g ½, 8kg → 4.9 mg/kg.
  - 34g × 3개 → 29.3, 병원 가기.
  - 초코파이 1개, 3.8kg → 23.6, 병원 가기.
  - 마늘 3쪽, 8kg → 5.6 g/kg, 물어보기.
  - 마카다미아 10알, 8kg → 3.50 g/kg, 병원 가기.
